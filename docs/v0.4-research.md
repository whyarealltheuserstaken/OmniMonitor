# OmniMonitor v0.4 — research & plan (draft, not implemented)

Status: research only. Nothing here is merged, released or built. Researched 2026-11-03 (PST).
Constraints carried forward: never fabricate numbers ("not available" instead); never read browser
cookies or OS keychains; API keys are never web-settable or exposed; competitors are inspiration only
(no code copied, even from MIT projects).

## 1. Dependencies & installer

### Options
| Option | Pros | Cons |
|---|---|---|
| **A. In-app first-run Setup wizard** (recommended) | Same unsigned binary we already ship; per-dependency consent; can detect what's present and only offer what the user enables; re-runnable from Settings | Must be built carefully (it executes installers) |
| B. Standalone .pkg (macOS) / .msi/.exe (Win) / .deb (Linux) that installs deps | Familiar "installer" UX | Unsigned .pkg is blocked by Gatekeeper just like the .app (user must right-click → Open / System Settings → Open Anyway); .pkg postinstall scripts run as **root**, so installing user-level tools (Grok CLI installs to the user's bin dir) from it is wrong; three installer toolchains to maintain; deps installed once at install time, not when a provider is enabled later |

Removing Gatekeeper friction for either option requires an Apple Developer ID ($99/yr) + notarization,
and Authenticode signing on Windows. That is a cost decision, not a technical one.

### Recommendation: A, plus nicer packaging (no dependency logic in packages)
- macOS: ship a **.dmg** (drag to Applications) instead of a zip; no .pkg unless we sign+notarize.
- Windows: keep the exe; optional Inno Setup installer later (Start-menu entry, autostart, uninstall).
- Linux: add AppImage next to the tar.gz.

### Setup wizard rules (security)
1. Detect only; nothing runs without an explicit click **per dependency**.
2. Only dependencies of providers the user turned on (Grok CLI is needed only for the Grok source; it is
   not "required" for the app).
3. Show the exact command and source before running. Allow-listed official sources only:
   - Grok CLI: `https://x.ai/cli/install.sh` (macOS/Linux), `https://x.ai/cli/install.ps1` (Windows),
     per https://docs.x.ai/build/overview. Both URLs returned HTTP 200 on 2026-11-03; the script header
     documents `curl -fsSL https://x.ai/cli/install.sh | bash`. npm package `@xai-official/grok` exists on
     the registry (alternative when Node is present).
4. Never pipe-to-shell. Download over HTTPS (certifi) to a temp file, show size + SHA256, offer "View
   script", then run `bash <file>` / `powershell -File <file>` as the current user (never sudo/admin).
5. Stream output into the wizard, log it to the app log, re-run detection afterwards and report the result.
6. HTTPS-only, no redirects off the allow-listed host. xAI publishes no checksum for install.sh, so we can
   only show the hash, not verify it (unverified gap; ask xAI or pin npm tarball integrity instead).

### Legitimacy legend
✅ local files written by the user's own tool, or an official documented API with a user-supplied key ·
⚠️ reuses another app's stored OAuth token or an undocumented endpoint (opt-in only, off by default, or skip) ·
❌ browser cookies, keychain, scraping, ToS-violating → **not supported**

## 4. Native app window

| Option | Size impact | Reuse of current UI | Fit |
|---|---|---|---|
| **pywebview** (recommended) | small (system WebView: WKWebView / WebView2 / GTK-WebKit) | reuses webui.py HTML/JS as-is | Python, stays in PyInstaller |
| PySide6 / Qt | +~100 MB+ (estimate) | full rewrite in Qt widgets/QML | native, heavy, LGPL |
| Tauri | small | reuse HTML, but needs a Rust shell + Python sidecar | two toolchains |
| Electron | +~100 MB+ | reuse HTML | Node runtime, heavy |
| Tkinter / customtkinter | tiny | rewrite; charts weak | dated look |

### Migration path
1. Keep pystray tray + CLI unchanged. Add `omnimonitor window` subcommand that opens pywebview on the
   existing 127.0.0.1 server.
2. **macOS main-thread constraint** (cause of the v0.3.0 SIGTRAP): both pystray and pywebview need the
   main thread. Launch the window as a **child process** from the tray ("Open Dashboard"), avoiding a
   shared run loop. Fallback to browser if pywebview fails.
3. Linux needs `python3-gi` + WebKit2GTK (or Qt). Detect and offer via the Setup wizard. Windows needs the WebView2
   runtime (built into Windows 11; offer the official Microsoft bootstrapper on Windows 10).
4. Restyle the UI as an app: sidebar (Dashboard, Providers, History charts, Settings, Setup), provider cards,
   charts (bundled lightweight chart lib, no CDN). API keys stay env/config-file only, never editable via the web layer.
